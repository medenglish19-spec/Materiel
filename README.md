# Fleet & Assets Manager — Materiel

نظام ويب متعدد المستخدمين لإدارة الأسطول والعتاد، مبني على معمارية معيارية (Modular) بحيث تُضاف أو تُعدّل الوحدات دون كسر بقية النظام.

## البنية

```text
app/
├── core/           # النواة: إعدادات، أمان، صلاحيات، dependencies
├── database/       # اتصال قاعدة البيانات وتهيئتها
├── shared/         # عناصر مشتركة عابرة للوحدات
└── modules/        # وحدات مستقلة حسب المجال
    ├── users/          # المستخدمون، الأدوار، تسجيل الدخول
    ├── equipment/      # العتاد والسيارات
    ├── equipment_types/# تصنيف أنواع/طرازات العتاد
    ├── maintenance/    # خطط وسجلات الصيانة
    ├── equipment_maintenance/
    ├── meter_readings/ # قراءات العدادات وتاريخها
    ├── faults_repairs/ # الأعطال والتصليحات
    ├── tires/          # الإطارات
    ├── batteries/      # البطاريات
    ├── fuel/           # الوقود
    ├── missions/       # المهمات
    ├── notifications/ # الإشعارات المركزية
    └── dashboard/      # لوحة التحكم

web/
├── main.py         # تشغيل وربط الراوترز
└── templates/      # القالب المشترك

static/             # CSS / JS / أصول الواجهة
migrations/         # Alembic migrations
tests/              # اختبارات النظام
```

## القاعدة المعمارية الحالية

- كل وحدة تحت `app/modules/<name>/` تحتوي طبقاتها المناسبة (`models`, `schemas`, `services`, `router`, `templates`) بحسب حجمها ووظيفتها.
- منطق الأعمال يجب أن يبقى في `services.py` عندما تكون طبقة الخدمات موجودة؛ والـ router يستقبل الطلب ويستدعي الخدمات.
- الربط بين الوحدات يمر عبر الخدمات قدر الإمكان لتقليل الترابط.
- `web/main.py` مسؤول عن تشغيل التطبيق وتسجيل الراوترز، وليس عن منطق الأعمال.
- قواعد الصيانة الوظيفية المرجعية محفوظة في `EXCEL_FUNCTIONAL_AUDIT.md`، ولا تُغيّر إلا عند وجود سبب مؤكد واختبارات تغطي التغيير.

## التشغيل محليًا

```bash
python -m venv venv
source venv/bin/activate   # ويندوز: venv\\Scripts\\activate
pip install -r requirements.txt
python run_web.py
```

التطبيق يعمل على `http://localhost:8000`.

## متغيرات البيئة

الإعدادات الحالية تعتمد على `DATABASE_URL` و`SECRET_KEY` و`APP_ENV` ومدة صلاحية الجلسة. راجع `app/core/config.py` قبل تشغيل بيئة إنتاجية.

> ملاحظة أمنية: إعداد حساب الإدارة الأولي وسياسة كلمة المرور قيد التشديد ضمن المرحلة الأمنية من خطة التطوير؛ لا تعتمد على أي بيانات اعتماد مكتوبة في التوثيق أو المصدر.

## قاعدة البيانات المحلية

قاعدة البيانات المحلية (`*.db`, `*.sqlite3`) ليست جزءًا من Git. أي بيانات أولية للتطوير يجب أن تُنشأ عبر أدوات/seed منفصلة، وليس عبر الالتزام بملف قاعدة بيانات محلي.

## الصيانة

مرجع الحالة التشغيلية والتغييرات المهمة موجود في `MAINTENANCE_STATUS.md`، بينما قواعد الوظائف المستمدة من نسخة Excel الأصلية موجودة في `EXCEL_FUNCTIONAL_AUDIT.md`.

## ملاحظات تطوير الصيانة والعتاد

### وحدة العتاد

- `asset_code` يتولّد تلقائيًا من رقم التسجيل عند توفره، أو من تسلسل مؤقت عند عدم توفره.
- نوع العتاد يحدد وحدة القياس (`km` أو `hours`) بدل الحقل القديم `has_hour_meter`.
- صفحة تفاصيل العتاد تعرض بيانات العتاد والعداد المناسب لنوعه.
- صفحة قائمة العتاد تدعم البحث والفلاتر وإظهار/إخفاء الأعمدة وحساب عدد النتائج.

### وحدة الصيانة

تدعم الوحدة أنواع الصيانة، خطط الصيانة الدورية، سجلات التنفيذ وقراءات العدادات التاريخية. تعتمد الاستحقاقات على بيانات العتاد الحالية وخطط الصيانة المرتبطة بالطراز/النوع وفق القواعد المعتمدة في المشروع.

`complete_maintenance_record()` يستخدم `measurement_unit == "hours"` عند التعامل مع عتاد الساعات، بدل الحقل القديم المحذوف.

### الإشعارات

تستخدم وحدة `notifications` نمط Provider Pattern؛ تسجّل كل وحدة مصدر إشعاراتها، ثم تجمعها الخدمة المركزية في شكل موحد مع مستوى الخطورة والرابط.

### قراءات العدادات

صفحة قراءات العدادات المقترحة تعتمد على `record_meter_reading()` لتحديث `current_odometer` أو `current_hours` وتسجيل القراءة التاريخية، مع بقاء هذه القيم مرجعًا لحساب استحقاق الصيانة.

## قرارات تصميمية مؤجلة

- تبسيط واجهة إعدادات الصيانة بحيث يكون اسم الخطة هو بند الصيانة نفسه.
- دعم أكثر من شرط تكرار للبند الواحد (مثل المسافة أو الزمن، أيهما يتحقق أولًا) مع الحفاظ على منطق الاستحقاق الحالي.
- بناء نظام صلاحيات مخصص ودقيق بعد استقرار الوحدات الوظيفية الأساسية.
- إعادة تنظيم `meter_readings` إذا استمر نموه، مع الحفاظ على الواجهات العامة الحالية.

## قواعد العمل

1. لا نغيّر منطق الأعمال العامل إلا عند وجود خلل مؤكد أو متطلب صريح.
2. كل إصلاح يجب أن يتبعه اختبار انحدار مناسب.
3. الاختبارات الكاملة يجب أن تمر قبل اعتبار المرحلة مكتملة.
4. لا تُستخدم ملفات قاعدة بيانات محلية أو بيانات اعتماد ثابتة في المستودع.
5. التوثيق يجب أن يعكس الحالة الفعلية للكود، وأي نقطة غير مؤكدة يجب تعليمها بوضوح بدل الافتراض.
